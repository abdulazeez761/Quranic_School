دروس الهندسة البرمجية والتحسينات المعمارية

تشريح الأخطاء الحقيقية، القرارات المعمارية، وفهم الأسباب الجذرية — ما وراء "Vibe Coding"

الفرق الجوهري بين Vibe Coding والهندسة البرمجية (Software Engineering): المبرمج السطحي (Vibe Coder) يرى العَرَض فيجرب تعديلات عشوائية حتى "يختفي الخطأ بالصدفة". المهندس الحقيقي (Software Engineer) يشرح السبب الجذري (Root Cause) في سياق المعايير والمواصفات القياسية (Standards)، ويكتب حلاً مبنياً على مبادئ الدفاع في العمق (Defense-in-Depth) والحتمية (Idempotency) وثبات السجلات (Immutability). فيما يلي توثيق تحليلي للتحسينات الستة المنجزة في النظام:
1

مشكلة الفاصلة العشرية في CSS وثنائية الثقافات (Culture-Invariant CSS Trap)

Views/Certificates/Components/_CertificateDynamic.cshtml & wwwroot/css/certificates/certificate.css
Vibe Coding: تغيير كود الشفافية عشوائياً حل مهندس: Invariant Culture + CSS Clamps

الأعراض والظاهرة: عند تعديل القالب أو عرض الشهادة في المتصفح، تحولت الزخرفة الإسلامية الخلفية (Damask Pattern) إلى لون ذهبي غامق مصمت بنسبة 100% طمس كل نصوص الشهادة وأسماء الطلاب.

التشخيص الهندسي العميق (Root Cause Autopsy): في بيئة ASP.NET Core Razor، عندما يعمل التطبيق في سياق ثقافة عربية (مثل ar-SA أو ar)، فإن دالة تحويل الأرقام العشرية إلى نصوص ToString() تستخدم الفاصلة , أو الفاصلة العربية ٫ بدلاً من النقطة . كفاصل عشري. وبالتالي، كود Razor: opacity: @patternOpacity; تحول في مخرجات الـ HTML إلى: opacity: 0,06;. وحسب المواصفة القياسية للغة CSS (W3C CSS Syntax Specification): الفاصلة , غير مسموح بها كفاصل عشري في قيم الخصائص الرقمية. بمجرد أن يقرأ المتصفح opacity: 0,06;، يعتبر السطر بالكامل خطأ صياغة (Syntax Error)، فيتجاهله ويعود للقيمة الافتراضية للخاصية وهي opacity: 1 (شفافية كاملة / لون مصمت 100%)!

قبل الحل (Vibe Coding — يعتمد على لغة الخادم الافتراضية)
<!-- في Razor: يعتمد على CurrentCulture -->
<div style="opacity: @patternOpacity;"></div>

<!-- النتيجة الفعلية في HTML تحت لغة عربية: -->
<div style="opacity: 0,06;"></div>
<!-- المتصفح يرفض السطر تماماً ويسقط إلى opacity: 1 -->
بعد الحل (Software Engineering — دفاع متعدد الطبقات)
<!-- الطبقة 1 (Razor): حتمية الفاصلة العشرية بالإنجليزية -->
<div style="opacity: @patternOpacity.ToString("0.000", CultureInfo.InvariantCulture);">

/* الطبقة 2 (CSS): حماية دفاعية دائرية مع clamp و mix-blend */
.cert-pattern-overlay {
    opacity: clamp(0.01, var(--cert-pattern-opacity, 0.05), 0.12) !important;
    mix-blend-mode: multiply;
}
القاعدة المعمارية المستفادة (Architectural Takeaway):
«أي رقم يتم توليده برمجياً ليُكتب داخل ملفات أو مخرجات تقنية (CSS، JSON، SVG، HTML Attributes، SQL Queries) يجب دائماً وأبداً أن يُنسق باستخدام CultureInfo.InvariantCulture، ولا يُترك للثقافة المحلية للمستخدم CurrentCulture تجنباً لاختلاف الفواصل العشرية».

التمركز الهندسي المطلق في ترويسة الشهادة (Symmetric CSS Grid vs Flexbox)

wwwroot/css/certificates/certificate.css (.cert-header)
Vibe Coding: ضبط الهوامش بـ Margin/Padding تقريبي حل مهندس: 3-Column Symmetric Grid (1fr auto 1fr)

الأعراض والظاهرة: البسملة في ترويسة الشهادة كانت تنزاح جانبياً ولا تستقر في منتصف الصفحة بالضبط، وتتغير إزاحتها باختلاف طول اسم المعهد أو طول رقم الشهادة وتاريخها.

التشخيص الهندسي العميق: عند استخدام display: flex مع 3 عناصر متباينة الطول الداخلي: الطرف الأيمن (اسم المعهد + الشعار = 190px)، والطرف الأيسر (الرقم المتسلسل + رمز التحقق QR + التاريخ = 270px). خاصية justify-content: space-between توزع المساحة المتبقية فقط، وبالتالي العنصر الأوسط (البسملة) لا يتمركز في منتصف الورقة، بل يُدفع نحو الجهة الأقصر مسافة بمقدار الفرق بين الطرفين!

قبل الحل (Flexbox — غير متناظر المحتوى)
.cert-header {
    display: flex;
    justify-content: space-between;
    align-items: center;
}
/* إذا كان الطرف الأيسر أعرض من الأيمن،
   فإن البسملة تنزاح عن منتصف الورقة! */
بعد الحل (Symmetric CSS Grid — قفل رياضي للمنتصف)
.cert-header {
    display: grid;
    grid-template-columns: 1fr auto 1fr; /* تماثل كامل للأطراف */
    align-items: center;
}
.cert-header-side:first-child { justify-self: start; }
.cert-basmalah { justify-self: center; text-align: center; }
.cert-header-side:last-child { justify-self: end; }
القاعدة المعمارية المستفادة:
«في الوثائق الرسمية والشهادات، لا تستخدم Flexbox لتوسيط عنصر بين عنصرين غير متساويين في الطول؛ بل استخدم شبكة CSS Grid بأعمدة متناظرة رياضياً grid-template-columns: 1fr auto 1fr; لقفل موضع العنصر الأوسط في المركز الهندسي الدقيق للورقة».

دورة حياة النوافذ المنبثقة وتجمد التمرير (Modal Scroll-Lock & Teardown Bug)

Areas/Admin/Views/CertificatesManagement/Index.cshtml & Students/Details.cshtml
Vibe Coding: إخفاء عنصر الحوار فقط بـ display:none حل مهندس: Teardown Lifecycle & Backdrop Cleanup

الأعراض والظاهرة: عند فتح نافذة الحذف أو الإلغاء للشهادة ثم إلغائها، تتجمد الصفحة تماماً ويصبح شريط التمرير (Scroll) غير مستجيب لأي حركة بالماوس أو الكيبورد.

التشخيص الهندسي العميق: عند فتح أي نافذة منبثقة، يقوم نظام النوافذ بتطبيق قفل على الـ DOM عبر خطوتين: 1. وضع overflow: hidden على عنصر <body> لمنع التمرير الخلفي أثناء الحوار. 2. إدراج عنصر تغطية شفاف أو شبه شفاف .modal-backdrop في نهاية الـ DOM. إذا تم إغلاق النافذة من خلال كود مخصص يغير فقط خاصية الحوار إلى display: none، دون استدعاء دورة حياة الإتلاف والتنظيف (Teardown Lifecycle)، يظل الـ <body> محبوساً بـ overflow: hidden ويظل عنصر الـ backdrop الشفاف يغطي كامل نافذة العرض ويمنع وصول أي أحداث نقر أو تمرير!

قبل الحل (إغلاق جزئي يترك آثاراً عالقة في الـ DOM)
function closeModal(id) {
    document.getElementById(id).style.display = 'none';
    // خطأ: لم تتم إزالة overflow:hidden عن body!
    // خطأ: عناصر backdrop ظلت عالقة تغطي الشاشة!
}
بعد الحل (دورة تنظيف شاملة ومضمونة Teardown)
function closeModalSafely(id) {
    const modal = document.getElementById(id);
    if (modal) {
        modal.style.display = 'none';
        modal.classList.remove('show');
    }
    document.body.classList.remove('modal-open');
    document.body.style.overflow = ''; // استعادة التمرير
    document.querySelectorAll('.modal-backdrop').forEach(el => el.remove());
}
القاعدة المعمارية المستفادة:
«أي مكون واجهة يعدل حالة عامة (Global State) مثل قفل الـ Body أو إضافة طبقات حظر تفاعل، يجب أن يمتلك دالة تنظيف وتفكيك حتمية (Deterministic Teardown) تُنفذ في جميع حالات الخروج أو الإلغاء دون استثناء».

فصل نية المستخدم عن التنفيذ المباشر (Decoupling Intent from Accidental Issuance)

Areas/Admin/Views/Students/Details.cshtml
Vibe Coding: رابط مباشر <a href="/Certificates/..."> يولد السجل فور النقر حل مهندس: Multi-stage Confirmation & Parameter Preview

الأعراض والظاهرة: سابقاً، كان مجرد النقر العرضي على رابط "تصدير الشهادة" يقوم فورياً بإنشاء السجل في قاعدة البيانات واستهلاك رقم رسمي متسلسل دون أي فرصة للمراجعة أو اختيار نطاق الأجزاء.

التشخيص الهندسي العميق: الشهادة كيان رسمي (Attested Credential) وليست مجرد صفحة عرض. توليدها ينتج عنه: 1. استهلاك رقم تسلسلي تدقيقي غير قابل للتكرار (مثل QRN-INS-00001). 2. إنشاء سجل تدقيق دائم CertificateAuditLog باسم المستخدم والوقت. 3. تجميد بيانات الطالب في لقطة JSON دائمة. دمج إعلان النية (Intent) مع التنفيذ المباشر (Execution) في نقرة واحدة ينتهك أبسط معايير هندسة تجربة المستخدم ومنع الأخطاء غير القابلة للعكس (Irreversible Action Prevention).

قبل الحل (نقر مباشر غير آمن يستهلك الأرقام)
<!-- نقرة واحدة عرضية تنشئ شهادة رسمية فوراً في الـ Database! -->

</a>

<!-- فصل النية: استدعاء نافذة التأكيد وضبط المعاملات -->
<button onclick="openConfirmQuranCertModal(this)">
    تصدير شهادة القرآن
</button>

     - فحص استباقي للشهادات السابقة
     - زر تأكيد نهائي واضح المعالم -->
القاعدة المعمارية المستفادة:
«العمليات الإنشائية ذات الأثر الرسمي أو المالي أو التدقيقي لا يجوز أبداً ربطها بنقرة واحدة غير خاضعة للتأكيد؛ بل يجب فصل نية المستخدم (Intent) عن التنفيذ الفعلي (Commitment) عبر نافذة حوار واضحة المعالم».

الفحص الاستباقي ومبدأ اللا تغيرية (Pre-Flight Checks & Idempotency Pattern)

Controllers/CertificatesController.cs & Services/CertificateIssuanceService.cs
Vibe Coding: توليد شهادة جديدة كلما طلب المشرف الطباعة حل مهندس: Idempotent Issuance + Pre-flight SweetAlert2

الأعراض والظاهرة: إذا كان الطالب يمتلك بالفعل شهادة رسمية سابقة معتمدة لنفس المتن أو نفس نطاق القرآن، يحتاج المشرف لتنبيه واضح يمنعه من توليد أرقام مكررة ويوفر له خيار عرض الشهادة السابقة فوراً.

التشخيص الهندسي العميق: تكرار إنشاء الشهادات لنفس الإنجاز يفسد سجلات المركز وسجل التدقيق ويزرع ارتباكاً في أرقام الاعتماد ورموز التحقق QR. لحل ذلك، تم تطبيق نمطين هندسيين متكاملين: 1. Pre-flight Verification (فحص استباقي في الفرونت-إند): استدعاء واجهات خفيفة CheckExistingQuran و CheckExistingMatn قبل فتح الحوار، لإظهار تنبيه SweetAlert2 تفاعلي يخير المشرف بين عرض الوثيقة السابقة أو الاستمرار. 2. Idempotent Service Handling (حتمية عدم التكرار في الباك-إند): في IssueQuranCertificateAsync و IssueMatnCertificateAsync، إذا كانت هناك شهادة لنفس الإنجاز بحالة نشطة Active، تعيد الخدمة نفس السجل وتفعل راية IsExistingCertificate = true دون إدراج أي سجل جديد في قاعدة البيانات.

نمط غير حتمي (Non-idempotent — ينشئ نسخاً مكررة)
// خطأ: كل استدعاء ينشئ رقماً تسلسلياً جديداً وسجل تدقيق جديد!
var data = await _legacy.GetMatnCertificateAsync(id);
return await PersistAsync(data, ...); // سجل مكرر في كل نقرة!
نمط حتمي (Idempotent — يضمن سلامة السجلات)
// فحص وجود شهادة نشطة مسبقاً
var existing = await _certificates.GetBySourceEntityAsync(progress.Id);
if (existing != null && existing.Status == CertificateStatus.Active)
{
    var model = ToModel(existing, baseUrl);
    model.IsExistingCertificate = true; // راية الإشعار
    return model; // إرجاع السجل الأصلي المعتمد دون تكرار
}
القاعدة المعمارية المستفادة:
«صمم عملياتك التوثيقية لتكون Idempotent؛ أي أن استدعاء العملية 10 مرات لنفس الإنجاز ينتج عنه نفس الحالة تماماً كالاستدعاء مرة واحدة، مع تقديم فحص استباقي Pre-flight للمستخدم لتجربة تفاعلية سلسة».

نمط التجميد واللاتغيرية في الوثائق (Immutability Pattern & Template Versioning)

Hafiz.Domain/Entities/Certificate.cs & CertificateTemplateVersion.cs
Vibe Coding: ربط الشهادة بالقالب الحي فقط عبر Foreign Key حل مهندس: Immutable JSON Snapshot + Version Entity

المعضلة المعمارية: لو أصدر المركز شهادة لطالب في عام 2024 بتصميم معين، ثم قام المشرف في عام 2026 بتعديل ألوان أو شعار أو خطوط القالب، هل يجوز أن يتغير شكل الشهادة الصادرة عام 2024 بأثر رجعي؟ قطعا لا!

الحل المعماري المعتمد: إذا اعتمدت الشهادة على القالب الحي (Live Reference)، فإن أي تعديل مستقبلي سيشوه أرشيف السجلات السابقة ويخرق الموثوقية القانونية والتوثيقية. تم حل ذلك عبر ركيزتين: 1. حقل التجميد CertificateDataJson: تخزين لقطة مجمدة كاملة للشهادة وكافة إعدادات القالب والنصوص لحظة النقر على الاعتماد. 2. كيان إصدارات القالب CertificateTemplateVersion: عند أي تعديل على القالب، يُنشأ إصدار جديد برقم تسلسلي متزايد (Version 1, Version 2...)، وتبقى الشهادات التاريخية مرتبطة بنسختها المجمدة للأبد.

القاعدة المعمارية المستفادة:
«في أي نظام يصدر وثائق رسمية، فواتير، أو عقود، لا تعتمد على العلاقات الحية فقط في قواعد البيانات؛ بل جمّد لقطة كاملة من الحالة (State Snapshot) كبيانات ثابتة (Immutable Data) تضمن استقلالية الماضي عن تعديلات المستقبل».

محرك الشهادات التقديرية العامة والشفاء التلقائي للقوالب (General Appreciation Engine & On-Demand Template Healing)

Services/CertificateIssuanceService.cs & DTO/DefaultTemplateConfigurations.cs
Vibe Coding: قوالب ثابتة مسبقة + استثناء Runtime إذا لم يُزرع القالب حل مهندس: Dynamic Token Resolution + On-demand Auto-seeding

المعضلة المعمارية: الشهادات التقديرية العامة (شكر وتقدير، تفوق دراسي، مواظبة، سلوك متميز) تتطلب مرونة كاملة في تخصيص عنوان الشهادة ومبرر/نص التكريم لكل طالب على حدة، دون كسر مبدأ اللاتغيرية (Immutability) ودون التعرض لاستثناء InvalidOperationException إذا لم يكن المركز قد زرع قالب الشهادة التقديرية مسبقاً في قاعدة بياناته.

الحل المعماري المتكامل: 1. الشفاء والتهيئة الذاتية للقوالب (Self-Healing Resolution): في دالة ResolveTemplateAsync، إذا لم تجد الخدمة قالباً افتراضياً مسجلاً للمعهد من النوع CertificateType.General، فإنها تقوم تلقائياً وعلى الفور بإنشاء القالب الافتراضي مع إصداره الأول من DefaultTemplateConfigurations.CreateDefaultGeneralConfig() وحفظه في قاعدة البيانات فورياً، مما يمنع تعطل عملية الإصدار تماماً في أي مركز. 2. حل الرموز الديناميكية (Dynamic Token Resolution): تم ضبط ترويسة العنوان في قالب التقدير على الرمز {CertificateTitle} بحيث يتكيف العنوان لحظياً مع خيار المشرف (شكر وتقدير / تفوق دراسي / عنوان مخصص). 3. حقن المبرر في اللقطة المجمدة (Closing Text Injection): في دالة PersistAsync، يتم حقن نص التقدير المخصص في data.Configuration.Tokens.ClosingText و ScopeDetails قبل التشفير التسلسلي إلى JSON، ليكون نص التكريم المخصص جزءاً أصيلاً وموثقاً في الوثيقة ورمز الـ QR للأبد.

قبل الحل (انهيار فوري عند عدم وجود القالب)
// إذا لم يُزرع القالب يدوياً للمعهد، تفشل العملية فوراً!
var template = await _templates.GetDefaultTemplateAsync(instId, type);
if (template == null)
    throw new InvalidOperationException("An active template is required.");
بعد الحل (شفاء ذاتي + تهيئة فورية على الطلب)
var template = await _templates.GetDefaultTemplateAsync(instId, type);
if (template == null && !templateId.HasValue)
{
    // تهيئة القالب الافتراضي فورياً دون انتظار Migration أو زرع يدوي
    var config = DefaultTemplateConfigurations.GetDefault(type);
    var newTemplate = new CertificateTemplate { ... };
    await _templates.AddAsync(newTemplate);
    await _templates.AddVersionAsync(new Version { ConfigurationJson = config.ToJson() });
    template = newTemplate;
}
القاعدة المعمارية المستفادة:
«صمم خدماتك الأساسية وفق مبدأ المقاومة والشفاء الذاتي (Self-Healing Services)؛ لا تعتمد فقط على وجود بيانات أولية مسبقة، بل اجعل نظامك قادراً على تهيئة بيئته التشغيلية تلقائياً عند أول طلب، مع إتاحة التخصيص المتغير فوق قالب مجمد متين».
8

محرك التخصيص الدقيق وتناغم المعاينة الحية مع الطباعة (Fine-Grained Customization Engine & View-Mirroring)

DTO/SectionConfig.cs & Views/Certificates/Components/ & certificate-template-builder.js
Vibe Coding: نصوص وإعدادات صلبة غير قابلة للتغيير في الكود حل مهندس: Declarative Config Contract + Dual Client/Server Rendering

المعضلة المعمارية: القوالب النموذجية تحتوي على عناصر ثابتة مشفرة داخل الـ Razor Views مثل: نص البسملة، غياب السطر الفرعي للعنوان، عدم إمكانية توثيق مرجع الآية القرآنية، عدم وجود بادئة لاسم الطالب (مثل: المكرم /، الطالب النجيب /)، وتنافر أحياناً بين ما يراه المستخدم في محرر الويب (Canvas Preview) وما يخرج فعلياً في أمر الطباعة المباشر window.print().

الحل المعماري المتكامل: 1. توسيع عقد الإعدادات الدقيقة (Fine-Grained DTO Contract): إضافة BasmalahText و ShowDate في ترويسة الشهادة، و Subtitle في العنوان، و Reference في الآية القرآنية، و StudentNamePrefix في بيان الإنجاز. 2. تطابق مخرجات العميل والخادم (Dual View-Mirroring): تم تحديث كل من مكونات Razor الجزئية (_HeaderSection, _TitleSection, _VerseSection, _StatementSection) وكود جافاسكريبت المباشر في certificate-template-builder.js ليولدا نفس هيكل الـ HTML ونفس فئات الـ CSS الدقيقة (.cert-title-subtitle, .cert-verse-ref, .cert-student-wrapper, .cert-header-date). 3. باليتات ألوان فاخرة متكاملة (Luxury Presets): إدراج ثيمات رفيعة المستوى (العقيقي الأندلسي الفاخر، الأونيكس الأسود والذهبي الملكي، الكهرماني التراثي) مع نمط الإطار الفاخر (Ornate Band Frame) والزوايا الأرابيسك المنقوشة.

«عند تصميم محركات القوالب والمستندات (Template Engines)، لا تفصل بين المعاينة الحية للواجهة (WYSIWYG Preview) ومخرجات الطباعة الحقيقية؛ اجعل كلاهما مرآة دقيقة للعقد نفسه (Configuration Contract) لضمان موثوقية النتيجة التامة دون أي مفاجآت عند التصدير».
